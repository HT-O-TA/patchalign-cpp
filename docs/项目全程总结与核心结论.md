# PatchAlign-Cpp 项目全程总结与核心结论

> 版本：2026-09-06；覆盖项目立项至 pre-A4 闭环完成和 exploratory A4 启动。
>
> 本文是项目经历与稳定结论的总入口，不维护分钟级作业进度。实时状态见[项目状态](status.md)，参数与阈值以 `configs/`、`schemas/` 和 ADR 为准，单次运行事实以集群 artifact manifest 为准。

## 1. 项目要解决什么问题

PatchAlign-Cpp 研究如何把开放权重代码模型训练成更可靠的 C++ 补丁生成器。输入是已经定位的 buggy function 或兼容的 file window、缺陷描述和有限失败证据；输出必须是一个纯 unified diff。模型不能看到 gold patch、fixed source、hidden test、chosen/rejected 标签或执行反馈。

项目没有把“文本看起来像补丁”当作成功。统一评分链为：

```text
冻结样本与 prompt
  → 模型生成 raw completion
  → 仅规范化一个缺失的终止 LF
  → strict diff 解析与路径策略检查
  → git apply --recount
  → 隔离编译
  → public test
  → hidden test
  → regression test
  → 固定分母聚合、配对比较与质量门禁
```

`--recount` 只忽略 diff 头声明的行号并重算上下文，不放宽删除行和上下文内容。任何 generation、parse、policy、apply、build、test 或 timeout 失败都保留在原分母中。

## 3. 阶段历程

### G0：真实模型综合 smoke

完成模型离线加载、BF16 LoRA、NF4 QLoRA、adapter 生命周期和生成 smoke。由此冻结 Base 模型身份、集群目录和专属 conda 环境，并确认后续实验可以在单张 A800 上运行。

核心结论：环境 smoke 是实验可行性证据，不是模型效果证据。

### A0：任务契约、Schema 与评分闭环

A0 在训练前冻结了任务边界：

- 第一阶段以 C++ function 为主，同时兼容 file-window 上下文；
- 输出只能是一个 unified diff，只允许修改指定文件；
- 建立 sample、prediction、execution 和 run manifest Schema；
- 正反例、确定性 fixture、解析/策略/apply/compile/test/timeout 分类全部进入自动测试；
- 固定 `git apply --recount` 语义和单个终止 LF 规范化边界；
- 冻结 SFT/DPO 提升阈值、退化上限、paired bootstrap 和 sanitizer 仅在明确适用样本上执行的政策；
- 冻结许可、数据发布、预训练污染披露和 artifact 哈希规则。

核心结论：先定义“什么算成功、什么算失败”，再训练模型，才能避免见到结果后改分母、改阈值或改评分。

### A1：数据来源与隔离 pilot

接入 CommitPackFT 与 RunBugRun，建立来源 revision、SHA256、许可证、repo/problem family 和 provenance 记录。首版 300 train + 50 validation pilot 在 A3.2 preflight 中暴露跨 split 泄漏：20 条 CommitPackFT validation payload 与 train 重复，另有 6 个 RunBugRun problem family 重叠。

随后重建 `pilot-v2-isolated`，保持 300/50 配额和来源比例，并在 repository family、sample、base commit、repo_id、provenance 五个维度实现 train/validation 零重叠。旧目录保留审计但禁止训练。

核心结论：随机划分不足以防止代码数据泄漏；必须按仓库族、问题族和提交身份做全局隔离。

### A2：安全执行与真实可重放评测

从 RunBugRun 构造候选，在 rootless Bubblewrap 中禁网、限资源、隔离编译并运行真实测试。只有 fixed 全部通过、buggy 存在目标失败、拥有足够 regression tests 且多次重放稳定的案例才能冻结。

最终 A2 holdout 包含 50 function + 20 file-window，共执行：

- regression tests：4,470；
- public target tests：518；
- hidden target tests：1,931。

70/70 在资格双回放和第三次独立回放中保持编译状态、退出状态、匹配结果、输出长度和 stdout/stderr SHA256 一致。一个读取未初始化内存的非确定性样本被明确排除。Job `93650` 完成最终证据。

核心结论：代码修复不能只比较文本相似度；真实 apply、compile、hidden 与 regression 执行才能区分格式正确和行为正确。

### A3.0：双基线 executable pilot

在同一 70 条 A2 pilot 上运行 Qwen2.5-Coder-7B Base（M0）和外部代码模型基线，固定 prompt、贪心 Pass@1、token 上限和 3 条确定性 probe。两者最终 Pass 都是 0/70。

这一步发现 56 个 strict diff 中有 55 个缺少终止 LF，导致部分本可应用的补丁被传输细节拒绝。原始 A3.0 artifact 保持不变，没有回填分数。

核心结论：0/70 不是“实验没用”，它建立了真实起点并暴露评分协议中的传输歧义。

### A3.1：scoring v2 与不可变预测重评分

ADR-0005 规定：仅当 raw completion 非空且缺少终止换行时追加恰好一个 LF，除此之外不改模型输出。无需重跑 GPU，直接对 A3.0 不可变预测重评分：M0 apply/compile 从 0 增至 2，外部基线从 0 增至 13，但两者 Pass 仍是 0/70。

核心结论：协议修正提高了评测公平性，但没有制造模型质量提升；原预测哈希和历史分数均保留。

### A3.2：BF16 LoRA 与 NF4 QLoRA pilot

使用隔离后的 300/50 数据，在同一 Base、seed、LoRA 结构和优化参数下公平比较两种训练方式，并各自重载 adapter、生成 70 条、运行 scoring v2：

| 模式 | parse/apply/compile/Pass | 结论 |
|---|---:|---|
| BF16 LoRA | 70/42/38/1 | 可运行 |
| NF4 QLoRA | 70/39/36/1 | 可运行 |

两者均为 1/70，未达到相差至少 2 条的质量优先条件，因此按预注册资源 tie-break 选择峰值显存更低的 NF4 QLoRA。该阶段只选择正式训练方案，不把 70 条结果包装成正式提升。

核心结论：当小样本质量无法区分时，应使用事先注册的资源规则，而不是事后挑选喜欢的方案。

### A3.3：正式 NF4 QLoRA SFT

正式数据冻结为 5,000 train + 500 validation；内部 executable holdout 为 400 function + 100 file-window，不参与 checkpoint 选择。长资格任务改为候选级原子 checkpoint，可在 Slurm 超时后恢复；token preflight 又剔除一个 9,876-token 超限样本，并据真实容量调整联合配额，未合成数据或降低过滤条件。

正式训练 Job `94340` 完成 1,875 optimizer steps，用时 `02:21:23`，最佳 checkpoint 为 epoch 2 / step 1,250。M1 在固定 500 条上的结果为：

- parse/apply/compile/Pass：499/391/373/15；
- function Pass：12/400，相对 M0 提升 +3pp；
- file-window Pass：3/100；
- paired-bootstrap 95% 区间：+1.5pp～+4.75pp；
- regression failure：5/500；
- timeout：3/500。

主提升门通过，但 timeout 相对 M0 增加 0.6pp，超过冻结上限 0.5pp，因此 `internal_gate_passed=false`。三个 timeout 经 CPU-only 同边界复现，buggy/fixed 均约 0.04 秒完成，而 M1 在 3 秒被杀死；根因包括死循环和复杂度爆炸。

核心结论：主指标提高不代表系统可靠；安全退化必须与 Pass 一起作为合取门禁。

### A3.4：SFT-R2 安全修正、独立确认与外部评测

SFT-R2 不读取 holdout 答案或失败样本参考修复，只从已冻结 A3.3 train/validation 静态选择循环、边界和复杂度风险模式，形成 1,200 train + 117 validation。从 M1 adapter 继续训练 1 epoch、150 optimizer steps，学习率 `2e-5`。Job `94524` 用时 15 分 15 秒，最佳 adapter SHA256 为 `8437acca...425a`。

M1-R2 在旧 500 条上的结果为：

- parse/apply/compile/Pass：499/412/392/14；
- function/file-window Pass：11/400、3/100；
- regression failure：3/500；
- timeout：2/500。

相对 M1，apply/compile 增加 21/19、regression 减少 2、timeout 减少 1，但总 Pass 从 15 降到 14；三个旧 timeout 中两个消失、一个保留，同时新增一个 timeout。相对 M0 的 function 提升为 +2.75pp，paired-bootstrap 95% 区间 +1.25pp～+4.5pp，旧 500 条 `internal_gate_passed=true`。

为了避免在已经分析过的旧 holdout 上自我确认，项目另行冻结 124 条未见确认集（100 function + 24 file-window）。M0 与 M1-R2 都是 0/124 Pass；M1-R2 虽显著改善 parse/apply/compile，却新增 3 条 regression failure 和 4 条 timeout。因此 `supplementary_confirmation_passed=false`，正式 A4 晋级被阻断。

Defects4C 外部流程从官方源得到 203 个 C++ function 候选，并排除与训练 family 重叠的 ArduinoJson 和 znc。源码准备和离线双资格最终得到：

- 176 条合格，27 条因 fixed 官方测试未通过而拒绝；
- 0 timeout、0 infrastructure error；
- 冻结分布：LLVM 139、cppcheck 31、EnTT 2、uncrustify 2、AtomicParsley 1、libzmq 1；
- manifest SHA256：`0728c602...28631`；
- prompts SHA256：`b23663fc...5484f`。

首次聚合 Job `94644` 因代码假设官方 prompt 只有一种结尾而失败。全量统计发现 44 条 complete-function、132 条 infill 模板；修复后只白名单这两个精确后缀，未知模板继续 fail closed，并在重提 Job `94925` 前遍历验证全部 176 条 prompt。外部配置随后锁死 176 条分母和两个哈希。

preflight Job `94927` 通过 241 项测试和全部身份检查；M0 Job `94928`、M1-R2 Job `94929` 均完成 176/176 冻结推理。首轮 CPU 评分暴露 rootfs 内 Python 导入路径不可见导致 runner 无结果 JSON；修复后替换数组 `95144` 完成全部评分。聚合结果为 M0 与 M1-R2 均 1/176 Pass、0 timeout，后者将 parse/apply/build 从 94/24/17 提升至 174/72/55，但没有提高最终 Pass。外部门禁只因无退化而通过。readiness 最终观测 internal=true、confirmation=false、external=true，保持 `a4_ready=false`。

核心结论：旧 holdout 通过与新确认集失败可以同时成立；前者证明可比性改善，后者否定了当前模型的未见分布晋级资格。

## 4. 项目中解决的代表性工程问题

| 问题 | 处理方式 | 可复述经验 |
|---|---|---|
| 无法直接使用 Docker/系统 Bubblewrap | 固定构建 rootless Bubblewrap，禁网、只读挂载、精确可写目录和资源限制 | 评测运行时本身也需要可复现和最小权限 |
| Slurm 秒退、空日志、`module` 不可用 | 参考集群有效作业语法，使用显式 conda prefix、`PYTHONNOUSERSITE=1` 和入口诊断 | 先区分调度/环境失败与模型失败 |
| 长资格任务超过时限 | 每个候选原子 checkpoint，重提时跳过已完成项 | 可恢复设计比盲目增加时限更可靠 |
| 训练/验证跨 split 泄漏 | 按 family、sample、commit、repo_id、provenance 五维隔离 | 代码数据必须做家族级去重 |
| 浮点输出格式被误判 | 复用 RunBugRun 官方兼容 matcher，并区分格式差异与真实异常 | 测试 oracle 也需要被验证 |
| raw diff 缺少终止 LF | 版本化 scoring v2，仅追加一个 LF，保留原始预测哈希 | 协议修复不能覆盖历史结果 |
| SFT 引入死循环/复杂度爆炸 | 固定 timeout 门禁、CPU 同边界复现、风险模式 R2 | 正确率和安全性必须联合优化 |
| 第三方 prompt 有两种官方模板 | 全量统计后精确双白名单，未知模板 fail closed | 单 fixture 通过不代表覆盖真实数据分布 |
| Defects4C 下载 DNS、慢 checkout、Git lock | 有限重试、900 秒 checkout、确认进程结束后精确清锁 | 恢复基础设施时不删除样本、不放宽门槛 |

## 5. 截至目前可以成立的核心结论

1. **训练显著改善了协议遵循，但端到端正确率仍低。** M0 在正式 500 条上全部 parse failed；M1/M1-R2 达到 499/500 可解析并大幅提升 apply/compile，但最终仅 15/500 和 14/500 Pass。
2. **可解析、可应用、可编译不是最终正确。** 每一层都是必要条件，hidden 与 regression 才能验证行为。
3. **旧 holdout 的提升不能外推为泛化。** M1-R2 在旧 500 条满足内部门禁，却在独立 124 条确认集上 0/124 且出现新的回归和超时。
4. **安全修正存在真实权衡。** R2 降低了汇总 timeout 和 regression，却损失一个 Pass，并发生风险样本迁移；不能仅看汇总数宣称问题已解决。
5. **负结果是项目成果的一部分。** 固定分母、预注册阈值、不可变预测和 fail-closed 检查使确认集失败无法被外部结果覆盖。
6. **外部证据具有分布限制。** Defects4C 冻结集 139/176 来自 LLVM；它比内部 RunBugRun 更接近真实仓库，但不能代表均衡的 C++ 生态。
7. **工程闭环比单次训练更具复用价值。** Schema、数据隔离、可恢复资格、GPU/CPU 解耦、哈希绑定和真实执行评分可继续服务 SFT、DPO 或其他 Base 模型。
8. **项目没有正式晋级 A4，但 exploratory A4 已启动。** 负责人授权的续行只用于构造可执行偏好数据和研究失败模式，不改变 `a4_ready=false`。

## 8. 一句话复述

这个项目的重点不是把一次微调包装成成功，而是建立一套不因结果难看而改变规则的 C++ 补丁训练与真实执行评测系统：SFT 大幅改善了 diff 协议和可编译性，但独立确认集揭示它尚未泛化，因此项目保留负结果，并只在明确的 exploratory 授权下继续 A4。
