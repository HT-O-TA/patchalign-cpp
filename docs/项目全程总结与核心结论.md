# PatchAlign-Cpp：项目全程总结与核心结论

## 1. 项目做了什么

PatchAlign-Cpp 研究如何让代码模型生成能够真实应用、编译并通过测试的 C/C++ 修复补丁。项目以 Qwen2.5-Coder-7B 为 Base，先通过监督微调学习补丁任务，再根据沙箱执行结果构造偏好数据进行 DPO，最后在固定协议下比较模型并完成冻结交付。

项目不是单纯的训练脚本集合，而是一条端到端实验链：

```text
任务与评分协议
    ↓
数据获取、清洗、去重与隔离切分
    ↓
LoRA / QLoRA 监督微调
    ↓
隔离沙箱中的 apply、compile、test
    ↓
根据真实执行结果构造偏好对
    ↓
DPO、消融、正式评测与失败分析
    ↓
模型卡、复现材料和冻结清单
```

## 2. 数据如何准备

训练数据来自 CommitPackFT 和 RunBugRun。两类数据互补：CommitPackFT 提供真实提交中的代码修改，RunBugRun 提供错误/正确程序对与可执行任务信号。

数据管线主要执行：

1. 字段标准化，将不同来源映射到统一 Schema。
2. 过滤缺失代码、未知许可证、过长源码、超长 token 和结构异常样本。
3. 按仓库家族、来源及上游划分进行隔离，避免同一项目的高度相似样本跨集合出现。
4. 使用固定随机种子进行分层抽样，使来源和任务层级比例可复现。
5. 输出数据清单、过滤报告、切分报告和 Schema 校验报告。

A1 pilot 包含 300 条训练样本和 50 条验证样本：训练集由 120 条 CommitPackFT 与 180 条 RunBugRun 组成，验证集由 20 条 CommitPackFT 与 30 条 RunBugRun 组成。它是固定种子的分层样本，不是无约束的纯随机抽取。

这些措施能降低显式泄漏风险，但不能证明预训练语料中不存在同源代码，也不能完全消除近重复、模板相似和项目家族相关性。因此项目对“无泄漏”的表述保持保守，并使用确认集和外部 Defects4C 检查跨分布表现。

## 3. A0 定义了什么

A0 将项目的任务、输入输出、评分和实验治理固定下来，避免训练后再改变成功标准。

- 任务：根据缺陷上下文生成统一 diff 补丁。
- 输出约束：补丁必须满足格式、文件范围和修改范围要求。
- 评分链：依次检查解析、应用、编译、公开测试、隐藏测试、回归测试与资源限制。
- 主指标：严格 Pass 数与 Pass 率。
- 辅助指标：Apply、Compile、各类测试失败、Timeout 和 Invalid Patch。
- 数据治理：记录来源、许可证、切分方法、去重策略和已知污染风险。
- 实验治理：冻结模型身份、提示模板、生成参数、随机种子、配置哈希和晋级门禁。

真实执行结果是最终依据；文本相似度、训练 loss 或补丁看起来是否合理都不能替代 Pass。

## 4. 为什么比较 BF16 LoRA 与 NF4 QLoRA

两者代表常见的参数高效微调取舍：

- BF16 LoRA 保留 BF16 基座计算，只训练低秩适配器，数值稳定且实现直接，但显存占用更高。
- NF4 QLoRA 将冻结的基座权重量化为 4 bit，再训练 LoRA，显著降低显存需求，但引入量化误差与额外实现复杂度。

项目比较它们，是为了回答“在现有集群资源下，节省显存是否值得潜在的效果和稳定性损失”。INT8 通常处于两者之间：显存节省不如 NF4 明显，而本项目已有 BF16 作为高精度基准、NF4 作为强压缩方案，继续加入 INT8 对核心决策的增量价值有限，因此没有把它设为主要实验臂。

pilot 中 BF16 LoRA 与 NF4 QLoRA 都取得 1/70 Pass，未达到“相差至少 2 条”的质量判定条件。项目因此不声称二者存在质量差异，而是按预注册的资源平局规则选择峰值显存更低的 NF4 QLoRA 进入正式 SFT。这个结论是本项目固定配置下的工程选择，不代表 NF4 在所有任务上都优于 BF16。

## 5. SFT 迭代解决了什么

M1 是第一版正式 SFT，使模型从不能产生严格可解析补丁的 Base，提升到能够大规模应用和编译补丁。正式集结果由 Base 的 0 Pass、0 Apply、0 Compile，提高到 15 Pass、391 Apply、373 Compile。

M1-R2 在 M1 基础上进一步调整训练和生成链，重点改善补丁服从性、应用率、编译率与稳定性。其正式集 Pass 为 14，略低于 M1 的 15，但 Apply 从 391 提高到 412、Compile 从 373 提高到 392、Timeout 从 3 降到 2。综合门禁因此选择 M1-R2 作为后续偏好数据和最终交付的基线。

这组结果说明：训练首先学会的是输出结构、局部编辑和编译约束；“能应用、能编译”改善得很明显，而真正通过语义测试仍然困难。

## 6. DPO 做了什么

A4 使用同一任务上候选补丁的真实执行结果进行排序，把表现更好的候选作为 `chosen`、更差的候选作为 `rejected`。偏好不是由文本风格或另一个模型主观打分决定，而是尽可能由 Apply、Compile、测试、回归和超时结果决定。

A5 比较不同 DPO beta。beta=0.3 的正式集表现最好：

| 模型 | Pass | Apply | Compile | Timeout |
|---|---:|---:|---:|---:|
| M1-R2 | 14/500 | 412 | 392 | 2 |
| DPO-beta0.3 | 19/500 | 437 | 424 | 5 |

DPO 提高了正式集 Pass、Apply 和 Compile，但 Timeout 增加了 0.6 个百分点，超过预设的 0.5 个百分点上限。项目因此保留 DPO-beta0.3 作为研究模型，并继续以 M1-R2 为默认模型。

## 7. 泛化结果说明什么

在确认集上，M1-R2 与 DPO-beta0.3 都是 0/124；在 Defects4C 上，两者都是 1/176。由此可以得出三个稳健结论：

1. 正式集提升是真实的，但主要集中在当前训练与评测分布。
2. 格式、应用和编译能力的改善，没有自动转化为跨项目语义修复能力。
3. DPO 优化了现有偏好信号，却没有突破外部分布瓶颈。

可能原因包括训练规模和任务覆盖不足、两个来源的数据形态不一致、自然语言任务上下文有限、可执行监督稀疏、项目级依赖缺失，以及预训练数据污染无法被完全观测。

## 8. 最终完成度

G0、A0 至 A5、A7 和 A8 均已完成；A6 的 RLVR/GRPO 经决策记录明确排除在本次交付范围之外。最终自动化测试为 446 项通过，交付清单覆盖 39 个 artifact。

默认交付模型是 M1-R2，DPO-beta0.3 是有价值但未通过稳定性门禁的研究结果。项目已达到“可展示、可解释、可审计、可复现”的交付状态，但不应包装成已经解决通用程序修复。

## 9. 简历与面试应掌握的概念

- SFT、LoRA、QLoRA、BF16、NF4 与参数高效微调。
- DPO 的 chosen/rejected 数据、beta 含义和偏好过拟合风险。
- 训练集、验证集、正式测试集、确认集和外部测试集的职责差异。
- 数据泄漏、近重复、仓库家族隔离和预训练污染边界。
- 统一 diff、补丁应用、编译、测试、回归和超时分类。
- 为什么主指标之外还需要稳定性门禁。
- 为什么正式集提高但外部集不提高，及其对泛化结论的限制。
- 配置冻结、哈希、运行回执、模型卡与可复现性。

## 10. 若继续推进，优先解决什么

1. 扩充具有完整仓库、构建脚本和测试的可执行训练任务。
2. 做更强的代码近重复与仓库谱系检查，并记录可能的预训练污染。
3. 增加项目级上下文、失败测试信息和检索能力，而不只使用局部代码窗口。
4. 针对确认集和 Defects4C 做错误分类，区分检索、定位、生成、编译和测试失败。
5. 在更广的开发集上选择 DPO 超参数，避免对单一正式集反复优化。
6. 只有在执行基础设施与奖励信号稳定后，再评估 RLVR/GRPO 是否值得投入。
